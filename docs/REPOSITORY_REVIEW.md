## Interface overlap and discrepancies

The integrated platform contract is `platform/ground/ui/src/contract/index.ts`, mirrored in `platform/shared/shared.ts` and `platform/shared/shared.py`. The separately maintained `argus-core/`, `contracts/`, and `mock-drone-agent/` components overlap with it but are not interchangeable.

| Area | Separate component behavior | Integrated platform behavior | Required boundary |
| --- | --- | --- | --- |
| Python module identity | Both `contracts/models.py` and `argus-core/contracts/models.py` occupy the import name `contracts.models`. The root module exposes Pydantic classes; the nested module exposes dependency-free validator functions such as `flight_plan()`. | Runtime uses TypeScript wire definitions plus Python `TypedDict` mirrors. | Never put both Python roots on one import path. Use component-specific entry points and adapt serialized values explicitly. |
| Waypoints | Root models use `alt`; `argus-core/` and the mock-agent schema use `alt_m`. Mock actions are `flyto` and `hover`. | Mission tools use canonical tool arguments and support `goto_gps`, `orbit_point`, `hold`, `rtl`, and newer tool names. Some executor aliases remain transitional. | Map `alt_m`/`alt` deliberately, map `flyto` to `goto_gps`, map `hover` to `hold`, and reject unknown actions. |
| Identity and time | Older records use `drone_id`/`mission_id` and ISO timestamps; mock JSONL also uses a sequence number and generic `type`/`payload`. | Wire envelopes require `vehicleId` and use epoch-millisecond `ts`; mission messages retain their documented nested envelopes. | Convert identity and time at ingestion. Never infer a vehicle from mutable global state. |
| Planning authority | Root contracts describe an intent-only mission specification followed by deterministic coverage planning. The mock schema permits planned waypoints. | The platform planner emits schema-bound mission tools and a deterministic verifier owns acceptance and correction. | Treat separate mission specifications as planning context and their flight plans as untrusted candidates. Only the platform verifier may authorize platform execution. |
| Verification and retry | Separate verdicts are `accept`/`reject`; mock orchestration supports up to three attempts and checks a different site/configuration. | Platform verdicts are `pass`/`corrected`/`rejected`; policy allows one retry and then escalation. | Map `reject` to `rejected`. Use `corrected` only when a corrected plan exists. Do not carry the three-attempt loop into platform runtime. |
| Site model | Separate fixtures use a different site and circular exclusion zones. | Platform runtime uses the Komati polygon, polygonal no-fly zones with vertical limits, staging data, clutter, and current reserve/range rules. | Revalidate every external plan against the current site. Never translate a separate pass verdict into a platform pass verdict. |
| Manual release | A separate control-handover model includes resume and abort release modes. | Platform manual disengage leaves the aircraft held; hostile-drone continuation requires the operator-only `continueMission` command. | Drop automatic-resume semantics at the adapter. Resume requires the explicit platform command and safety gates. |
| Sensor and readiness data | Separate state, detection, and observation records do not carry the platform sensor-health, navigation-source, sortie, readiness, RF, and frame-reference fields. | Platform envelopes model those fields explicitly. | Preserve absent state as unknown or unavailable. Never fabricate healthy sensors or readiness. |
| Event transport | The root model uses a generic hub event; the mock agent uses JSONL. | Platform runtime uses discriminated WebSocket envelopes and audit records. | Decode external transport into typed platform messages before it crosses the runtime boundary. |

Useful one-way mappings are: detection to anomaly; flight plan to mission plan; validation result to verification; drone state to telemetry and fleet vehicle; observation to observation message; incident report to incident-report envelope; and clamp records to command acknowledgements or verification edits. Polygon evidence, narrative fields, and unknown fields should remain in adapter metadata rather than being silently discarded or promoted to trusted runtime state.

## Consolidated layout

The integrated runtime moves as one unit under `platform/`; the team's other active components remain separate roots:

```text
platform/
  companion/
  ground/
  shared/
  sim/
  site/
  scripts/
  verifier_fixtures/
argus-core/
contracts/
mock-drone-agent/
.github/
docs/
```

Moving the runtime sibling directories together preserves existing `../../site` references, Vite aliases, Electron sibling paths, and scripts that derive the runtime root from their own directory. Runtime-local `Makefile`, `justfile`, environment examples, requirements, platform documentation, and imported design assets move with `platform/`. Cross-component decisions and specifications stay in root `docs/`.

Keep `.github/` at the repository root and configure workflows to:

- run UI jobs in `platform/ground/ui` and cache `platform/ground/ui/package-lock.json`;
- publish `platform/ground/ui/dist`;
- install and cache the companion from `platform/companion/pyproject.toml`;
- prefix Ruff and pytest targets with `platform/`;
- invoke the simulator with `bash platform/scripts/run-sim-e2e.sh`;
- review Docker build contexts and every documented root-relative command after the move.

There is no root JavaScript workspace whose package resolution needs preservation. Local package manifests move with their applications. Tracked `__pycache__` directories and `.pyc` files were removed by the consolidation cleanup and remain excluded by `.gitignore`; earlier versions remain in Git history.

Current documentation and runtime surfaces use the current product identity. NVIDIA's `nvarguscamerasrc` is an API identifier and must not be altered by branding cleanup.

## Authority after consolidation

The authoritative platform wire contract remains `platform/ground/ui/src/contract/index.ts`, with reviewed mirrors in `platform/shared/`. Planner-specific mirrors require parity tests. Separate components need explicit adapters; their contracts and verifiers do not become platform authority through import-path precedence.
